# TASK-1126 — Frontend Platform Architecture & Certification

## Objective
Design and certify the complete frontend platform architecture for AtlasAI, covering Web, Android, iOS, and Browser Extension from a single Turborepo monorepo. Every technology decision is final, Context7-verified, and immutable for all subsequent implementation work.

## Phase 5 — API Integration Layer

### Layer Architecture

```
Browser / App / Extension
        │
        ▼
  @atlas/hooks (TanStack Query)
  - useQuery, useMutation, useInfiniteQuery
  - Cache invalidation, prefetching
  - SSR hydration
        │
        ▼
  @atlas/api-client (openapi-fetch)
  - Typed fetch wrapper
  - Auth interceptor (token injection + refresh)
  - SSE client (EventSource wrapper)
  - Upload client (multipart/form-data)
  - Download client (blob/binary)
  - Error mapper (API errors → @atlas/errors)
        │
        ▼
  Backend API (54 endpoints)
```

### Auth Interceptor Flow

```
1. Request intercepted by openapi-fetch middleware
2. Access token attached from @atlas/auth Zustand store
3. If 401 response:
   a. Attempt refresh via /auth/refresh
   b. If refresh succeeds: update Zustand store, retry original request
   c. If refresh fails: clear Zustand store, redirect to login
4. If 401 on refresh itself → logout immediately
5. Concurrent 401s: single refresh request, queue others
```

### SSE Streaming

```
POST /api/v1/ai/chat/stream

1. @atlas/api-client/sse-client.ts creates ReadableStream from fetch()
2. @atlas/hooks/ai.ts: useStreamChat hook manages:
   - Connection lifecycle (open, streaming, error, done)
   - Accumulated response buffer
   - Abort controller
   - Auth token injection
3. App consumes: { data, stream, isStreaming, error, abort }
```

### Upload Flow

```
POST /api/v1/knowledge/documents (multipart/form-data)

1. React Hook Form collects file + metadata
2. @atlas/api-client/upload-client.ts:
   - Creates FormData
   - Sets Content-Type: multipart/form-data
   - Tracks upload progress
   - Injects auth token in query param (multipart can't set Authorization header on some platforms)
3. @atlas/hooks: useUploadDocument mutation
```

## Phase 6 — State, Forms & Validation Architecture

### State Management Layers

```
Layer                 Tool              Scope            Persistence
─────────────────────────────────────────────────────────────────────
Server State          TanStack Query    API data         In-memory + optional AsyncStorage
Client State          Zustand           Auth, UI, prefs  Secure storage / localStorage
Form State            React Hook Form   Individual forms None (unmanaged)
URL State             Expo Router /     Route params     URL
                      Next.js Router
Cache State           TanStack Query    Query cache      Optional persister
                      Persist
```

### Zustand Stores

```
@atlas/auth/src/store.ts:
  - accessToken: string | null
  - refreshToken: string | null
  - user: User | null
  - isAuthenticated: boolean
  - login(tokens, user)
  - logout()
  - setTokens(tokens)
  - Persist: expo-secure-store (mobile), chrome.storage (extension), in-memory (web — no localStorage for JWT)

App-level stores (NOT in shared packages, per-app):
  - themeStore (Zustand + persist)
  - sidebarStore (Zustand)
  - preferencesStore (Zustand + persist — syncs to PATCH /users/preferences)
```

### Form Validation Pattern

```
Schema: Zod (source of truth)
  │
  ▼
Resolver: @hookform/resolvers/zod → React Hook Form
  │
  ▼
UI: @atlas/ui primitives (Input, Select, DatePicker, etc.)
  │
  ▼
Submission: @atlas/api-client typed mutation → TanStack Query
```

- Shared validation schemas in `@atlas/api-client/src/schemas/` (e.g., `loginSchema`, `registerSchema`, `documentSchema`)
- These are generated from OpenAPI spec or hand-written for auth flows where OpenAPI lacks request body schemas
- Reuse `@atlas/validation` predicates within Zod refinements (e.g., `z.string().refine(isEmail)`)

## Phase 7 — Offline & Caching Strategy

### Web (Next.js)

| Mechanism | Implementation | Scope |
|-----------|---------------|-------|
| Service Worker | next-pwa or workbox | Static assets, API cache fallback |
| TanStack Query Persist | localStorage persister | Query cache survival across page reloads |
| Zustand Persist | localStorage (non-sensitive only) | Theme, preferences, sidebar |
| No offline mutations | Degrade gracefully | Show "offline" banner, queue not supported |

### Mobile (Expo/React Native)

| Mechanism | Implementation | Scope |
|-----------|---------------|-------|
| AsyncStorage | TanStack Query experimental_createQueryPersister | Query cache (12h TTL) |
| Secure Store | expo-secure-store | Refresh token |
| Zustand Persist | AsyncStorage adapter | Preferences, theme |
| NetInfo | @react-native-community/netinfo | Show offline indicator |
| Offline mutations | Not supported (MVP) | Future: mutation queue with background sync |

### Extension (WXT)

| Mechanism | Implementation | Scope |
|-----------|---------------|-------|
| chrome.storage.local | Zustand persist storage | Auth tokens, preferences |
| TanStack Query Persist | chrome.storage.local adapter | Limited cache |
| Background sync | Service worker | Future: periodic sync |

### Authentication in Extension

```
1. Popup opens → check chrome.storage for tokens
2. If tokens exist → hydrate @atlas/auth Zustand store
3. If tokens expired → background worker refreshes
4. If no tokens → show login form (same React Hook Form + Zod)
5. Login calls POST /auth/login via @atlas/api-client
6. Tokens stored in chrome.storage.local
7. Content script → background → API communication via chrome.runtime messaging
```

## Phase 12 — Architecture Decision Records

### ADR-021 — Next.js (Web Framework)

**Status:** Accepted
**Context:** AtlasAI requires a production web application with SSR, SEO, streaming, and excellent developer experience.
**Decision:** Next.js 14+ with App Router (React Server Components, Streaming SSR, Route Handlers, Middleware).
**Alternatives Rejected:** Remix (less streaming support), Vite + React (no SSR without additional setup), CRA (deprecated).
**Consequences:**
- Server Components reduce client bundle size
- Middleware enables efficient auth checks
- Streaming SSR enables progressive loading for AI chat responses
- Must carefully separate server/client component boundaries
- Good — Next.js is the most mature React meta-framework with strong community support

### ADR-022 — Expo (Mobile Framework)

**Status:** Accepted
**Context:** AtlasAI requires iOS and Android applications that share maximum code with the web application.
**Decision:** Expo SDK 52+ with Expo Router, EAS Build, expo-updates (OTA), and expo-secure-store.
**Alternatives Rejected:** Bare React Native (no OTA updates, harder CI/CD, more boilerplate), React Native CLI (same limitations).
**Consequences:**
- Expo Router provides file-based routing shared with web navigation patterns
- EAS Build provides CI/CD for mobile app stores
- OTA updates enable instant bug fixes without app store review
- expo-secure-store provides platform-native encrypted storage for refresh tokens
- Must use Expo's managed workflow or prebuild; bare workflow available if native modules needed
- The Expo ecosystem is mature enough for enterprise production apps (SDK 52+)

### ADR-023 — Tamagui (Cross-Platform UI)

**Status:** Accepted
**Context:** AtlasAI needs a single design system that works identically on Web, iOS, Android, and Browser Extension.
**Decision:** Tamagui with optimizing compiler as the shared UI framework. Tamagui tokens for theming. @tamagui/core primitives as base. Custom components built with `styled()`.
**Alternatives Rejected:** NativeWind (TailwindCSS for RN — no UI kit, separate web/mobile code, lower benchmark score 74.24 vs 83.05), plain TailwindCSS (web only), React Native Paper (web support is weak).
**Consequences:**
- Positive: 100% API parity between React Native and Web
- Positive: Optimizing compiler generates atomic CSS for web, hoisted style objects for native
- Positive: Built-in UI kit (Button, Input, Sheet, Dialog, Toast, etc.)
- Positive: Cross-platform theming with dark/light mode
- Positive: Monorepo-friendly with `tamagui.dev` docs
- Trade-off: Tamagui compiler adds build step
- Trade-off: Learning curve for Tamagui's `styled` API vs Tailwind utility classes
- Trade-off: Smaller community than TailwindCSS

### ADR-024 — TanStack Query (Server State)

**Status:** Accepted
**Context:** AtlasAI needs robust server state management with caching, deduplication, retry, pagination, infinite scroll, and SSR hydration across web and mobile.
**Decision:** TanStack Query v5 with QueryClient, useQuery, useMutation, useInfiniteQuery, and experimental_createQueryPersister for offline persistence.
**Alternatives Rejected:** SWR (fewer features, less mature TypeScript support, no devtools).
**Consequences:**
- Automatic caching and deduplication reduces API calls
- useInfiniteQuery enables chat history pagination
- SSR prefetchQuery + dehydrate enables server-rendered pages with immediate interactivity
- React Native AppState integration via focusManager.setFocused
- Offline persistence via experimental_createQueryPersister
- Good: Vast ecosystem, excellent TypeScript support, React Native support

### ADR-025 — Zustand (Client State)

**Status:** Accepted
**Context:** AtlasAI needs lightweight client-side state management for auth tokens, UI preferences, theme, and sidebar state without boilerplate.
**Decision:** Zustand v5 with persist middleware. Auth tokens in platform-appropriate secure storage. UI preferences in localStorage/AsyncStorage.
**Alternatives Rejected:** Redux Toolkit (too much boilerplate for this use case), Jotai (atomic state adds complexity for simple state needs), Context (re-rendering performance issues).
**Consequences:**
- Minimal boilerplate — stores are functions, not classes with reducers
- persist middleware handles serialization/deserialization automatically
- devtools middleware enables Redux DevTools debugging
- TypeScript inference is excellent with `create<Store>()()` pattern
- Zustand v5 requires explicit setState after store creation for initial values
- Good: 1.1 KB bundle size, no provider needed, framework-agnostic

### ADR-026 — React Hook Form + Zod (Forms & Validation)

**Status:** Accepted
**Context:** AtlasAI requires performant, TypeScript-safe form handling with validation across all platforms (web, mobile, extension).
**Decision:** React Hook Form v7 with @hookform/resolvers/zod resolver. Zod schemas as the single source of truth for form validation, shared between client and server.
**Alternatives Rejected:** Formik (re-renders entire form on any change), Final Form (less TypeScript support), custom validation (duplication).
**Consequences:**
- Unmanaged form state — no re-renders on keystroke
- Zod schemas provide inferred TypeScript types automatically
- Resolver pattern enables platform-agnostic validation
- Controller component wraps Tamagui/React Native components
- Good: Zod schemas can be shared with backend validation (future)
- Good: TypeScript inference from Zod transforms

### ADR-027 — openapi-typescript + openapi-fetch (API SDK)

**Status:** Accepted
**Context:** AtlasAI needs a type-safe API client generated from the backend OpenAPI 3.0 specification (54 endpoints).
**Decision:** openapi-typescript (CLI) for type generation from `openapi.json`. openapi-fetch (runtime) for the typed fetch wrapper. Generated types stored in `@atlas/api-client/src/types.ts`.
**Alternatives Rejected:** orval (generates React Query hooks — reduces control, heavier), OpenAPI Generator (requires Java, heavier), manual types (maintenance burden).
**Consequences:**
- Types are generated, never hand-written — guaranteed to match backend
- openapi-fetch provides 0.8 KB typed fetch wrapper
- Generated types used directly in TanStack Query generic parameters
- Missing response types (28 endpoints return Promise<unknown>) require manual type overrides in `@atlas/api-client/src/types.ts`
- `noUncheckedIndexedAccess` must be enabled in tsconfig
- Generation script runs as part of CI or manually when OpenAPI spec changes

### ADR-028 — WXT (Browser Extension)

**Status:** Accepted
**Context:** AtlasAI requires a browser extension (Chrome, Firefox, Edge, Safari) that shares code with the web and mobile apps.
**Decision:** WXT with @wxt-dev/module-react for React/TypeScript support. MV3 for Chrome, MV2 fallback for Firefox. Popup + Side Panel + Content Script architecture.
**Alternatives Rejected:** CRXJS (Manifest V3 only, no multi-browser auto-publishing, less monorepo-friendly, Score: 80.63 vs WXT 78.51 but WXT has better monorepo integration), Plasmo (less mature, smaller ecosystem), Vanilla Webpack (no HMR, manual).
**Consequences:**
- File-based entrypoints (popup/, sidepanel/, background.ts, content.ts)
- HMR during development
- Multi-browser support (Chrome, Firefox, Edge, Safari)
- Auto-publishing via WXT CLI
- chrome.storage.local for persistence
- Shares @atlas/api-client, @atlas/auth, @atlas/ui (minimal subset)
- Trade-off: WXT is newer than CRXJS (fewer GitHub stars, smaller community)
- But: better monorepo integration, MV2+MV3 support, TypeScript-first

### ADR-029 — Storybook + Chromatic (Visual Testing)

**Status:** Accepted
**Context:** AtlasAI needs component documentation, visual regression testing, and design system review workflow.
**Decision:** Storybook 8 for Next.js (web components) + Tamagui Studio for shared components. Chromatic for visual regression testing and review workflow.
**Alternatives Rejected:** Ladle (less mature), Histoire (no Tamagui integration).
**Consequences:**
- Storybook provides component isolation and documentation
- Chromatic provides visual diffs, review workflow, cross-browser screenshots
- Tamagui components render in Storybook via @storybook/react + Tamagui config
- Chromatic auto-accepts on main branch, requires review on PRs

### ADR-030 — Vitest + Playwright + Detox (Testing)

**Status:** Accepted
**Context:** AtlasAI requires comprehensive testing across all platforms: unit, integration, web E2E, mobile E2E, and visual regression.
**Decision:**
- Vitest (unit + integration) — already in monorepo, Vite-native, Jest-compatible
- Playwright (web E2E) — cross-browser, mobile viewports, auto-wait, TypeScript
- Detox (mobile E2E) — gray-box, async monitoring, iOS simulator + Android emulator
- Storybook + Chromatic (visual regression)
**Alternatives Rejected:** Jest (slower, more config for new projects), Cypress (Chromium only, no mobile), Appium (slow, flaky, less integrated).
**Consequences:**
- Vitest: 80% coverage threshold, jsdom environment for frontend packages
- Playwright: Three browser projects (chromium, firefox, webkit) + two mobile (Chrome, Safari)
- Detox: iOS simulator (iPhone 15 Pro) + Android emulator (Pixel_4_API_30)
- All E2E tests run in CI after quality gate

### ADR-031 — i18next (Internationalization)

**Status:** Accepted
**Context:** AtlasAI supports 6 locales (en-US, ru-RU, de-DE, fr-FR, ja-JP, zh-CN) and needs a scalable internationalization solution.
**Decision:** i18next with react-i18next for React integration. ICU message format. Namespace-based translation files. Lazy loading per locale.
**Alternatives Rejected:** react-intl (less flexible ICU support), LinguiJS (smaller ecosystem).
**Consequences:**
- Translation files in `@atlas/i18n/src/locales/{locale}/{namespace}.json`
- Namespaces: common, auth, chat, knowledge, prompts, settings, errors, extension
- react-i18next useTranslation hook provides TypeScript-safe translation keys
- Locale detection: browser preference → stored preference → en-US fallback
- Good: Mature ecosystem, ICU format, React Suspense integration

### ADR-032 — Turborepo + Changesets (Build & Release)

**Status:** Accepted
**Context:** AtlasAI monorepo needs efficient build orchestration and automated semantic versioning.
**Decision:** Turborepo (already established) for build caching and parallel execution. Changesets for versioning, CHANGELOG generation, and publishing.
**Alternatives Rejected:** Nx (heavier, more configuration), Lerna (maintenance mode), semantic-release (less pnpm monorepo support).
**Consequences:**
- Turborepo remote cache for CI speed
- Changesets generated per PR, versioned on merge to main
- Automatic CHANGELOG generation
- Semantic versioning (major.minor.patch) for packages
- GitHub Actions releases workflow

## Phase 14 — Risk Assessment

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| **Performance — Tamagui compiler** | Low | Medium | Compiler runs in CI/CD, cached by Turborepo. Dev mode uses unoptimized Tamagui. |
| **Performance — Bundle size** | Low | Medium | Next.js RSC, Tamagui tree-shaking, dynamic imports, bundle analyzer in CI. |
| **Scalability — Query cache** | Low | Low | TanStack Query handles thousands of cache entries. Infinite scroll pagination limits data. |
| **Scalability — SSE streaming** | Medium | Medium | Single SSE connection per chat. Abort controller for stale connections. |
| **Maintenance — OpenAPI drift** | High | High | CI runs `generate-api-types.sh` on OpenAPI change. Fails if spec is invalid. Manual review on spec update. |
| **Maintenance — Dependency updates** | Medium | Medium | Renovate/Dependabot for automated PRs. Changesets for versioning. |
| **Vendor Lock-in — Expo** | Low | Medium | Expo uses standard React Native under prebuild. Eject capability exists but costly. |
| **Vendor Lock-in — Tamagui** | Medium | High | Tamagui compiler is proprietary optimization. Fallback: use Tamagui without compiler (slower). |
| **Vendor Lock-in — WXT** | Low | Medium | WXT outputs standard extension builds. Migration to CRXJS/Plasmo is rewrite but architecture remains. |
| **Migration — Next.js to new framework** | Low | High | Next.js is mature. Migration path would require full rewrite but shared packages remain intact. |
| **Testing — Mobile E2E flakiness** | Medium | High | Detox reduces flakiness via async monitoring. Retry failed tests (max 2). Quarantine flaky tests. |
| **Testing — Visual regression noise** | Medium | Low | Chromatic's review workflow handles intentional changes. Cross-browser differences are expected. |
| **Offline — Mutation queue** | High | Low | Offline mutations deferred to future milestone. MVP shows offline banner only. |
| **Offline — Cache invalidation** | Medium | Medium | TTL-based cache (12h) may show stale data. "Pull to refresh" available on all list views. |
| **Browser Extension — API compatibility** | Low | Medium | Extension uses same @atlas/api-client. CORS handled via host_permissions in manifest. |
| **Browser Extension — Storage limits** | Medium | Medium | chrome.storage.local limit is 10 MB per extension. Tokens and preferences are well under. |
| **Mobile — Secure storage availability** | Low | High | expo-secure-store requires physical device or simulator. Fallback for testing environments. |
| **Mobile — App store review** | Medium | Medium | Plan for 3-5 day review. OTA updates for urgent fixes. |
