## Context7 Findings

### Finding C1 — Prisma Error Handling Gap (Medium)

| Field | Value |
|-------|-------|
| **Severity** | Medium |
| **Affected files** | All services using Prisma (PrismaService, DocumentService, PromptService, MetadataService, OrganizationService, etc.) |
| **Why it's a problem** | `PrismaClientKnownRequestError` (e.g., P2002 unique constraint, P2025 record not found) is never caught anywhere in the codebase. When Prisma throws these expected operational errors, they propagate to the `GlobalExceptionFilter` as unknown errors → `500 Internal Server Error` with code `INTERNAL_ERROR`. For example, a duplicate email registration causing P2002 returns 500 instead of 409 Conflict. |
| **Context7 reference** | NestJS Prisma recipe recommends handling Prisma errors explicitly: "It is recommended to abstract the Prisma Client API for database queries" and to handle database errors in service layers. The Prisma documentation recommends catching `PrismaClientKnownRequestError` for expected operational errors. |
| **Recommended fix** | Add a Prisma exception filter (`@Catch(PrismaClientKnownRequestError)`) that maps Prisma error codes to HTTP statuses: P2002 → 409 Conflict, P2025 → 404 Not Found, P1001 → 503 Service Unavailable. Register it alongside the GlobalExceptionFilter. |

### Finding C2 — getErrorCode Status Map Incomplete (Low)

| Field | Value |
|-------|-------|
| **Severity** | Low |
| **Affected files** | `common/filters/global-exception.filter.ts:47-54` |
| **Why it's a problem** | The `getErrorCode` function maps HTTP status codes to error code strings for `HttpException` instances. `UNPROCESSABLE_ENTITY` (422) and `SERVICE_UNAVAILABLE` (503) are missing from the map. The `ValidationPipe` throws `UnprocessableEntityException` when DTO validation fails, which results in code `"HTTP_ERROR"` instead of `"VALIDATION_ERROR"`. Service-layer `ValidationError` (from `@atlas/errors`) correctly returns `"VALIDATION_ERROR"` because AppError is checked first, creating an inconsistency between pipe-level and service-level validation errors. |
| **Context7 reference** | NestJS exception filters documentation: "Exception filters provide full control over the exception layer, allowing developers to customize error responses." A complete status map is expected for consistent error codes. |
| **Recommended fix** | Add `[HttpStatus.UNPROCESSABLE_ENTITY]: "VALIDATION_ERROR"` and `[HttpStatus.SERVICE_UNAVAILABLE]: "SERVICE_UNAVAILABLE"` to the status map. |

### Finding C3 — Configuration Not Centralized (Informational)

| Field | Value |
|-------|-------|
| **Severity** | Informational |
| **Affected files** | `config/config.module.ts`, `prisma/prisma.service.ts`, `redis/redis.service.ts`, `providers/*/openai.provider.ts` |
| **Why it's a problem** | The codebase uses `process.env` reads scattered across 10+ files instead of a centralized configuration module with validation. The `ConfigLoader` from `@atlas/config` exists and is used in `main.ts` for `PORT`/`HOST` but not extended to cover other env vars. NestJS recommends using `ConfigModule.forRoot()` with Joi validation for centralized config management. |
| **Context7 reference** | NestJS Configuration documentation: "Define a Joi validation schema for environment variables" and "Custom validate function" for fail-fast boot validation. |
| **Recommended fix** | Already documented as deferred in TASK-1118. No immediate action needed. |

## Security Findings

### Finding S1 — Provider Error Body Leaked in Error Message (Medium)

| Field | Value |
|-------|-------|
| **Severity** | Medium |
| **Affected files** | `ai-gateway/services/ai-gateway.service.ts:148-153` |
| **Why it's a problem** | When an AI provider returns an error, the `ai-gateway.service.ts` throws `new ForbiddenException({ error: AiGatewayErrorCode.PROVIDER_ERROR, message: result.error.message, statusCode: result.error.statusCode })`. The `result.error.message` may contain the raw response body from the external AI provider API (e.g., OpenAI error details), which could include sensitive information, internal model IDs, or billing information from the provider. The `GlobalExceptionFilter` passes this through as the `message` field in the HTTP response. |
| **Risk** | Information disclosure — external provider error details are forwarded to the API client without sanitization. |
| **Recommended fix** | Sanitize provider error messages before including them in HTTP responses. Log the full error internally, but return a generic message like "AI provider temporarily unavailable" to the client. |

### Finding S2 — No Correlation ID in Error Responses (Low)

| Field | Value |
|-------|-------|
| **Severity** | Low |
| **Affected files** | `common/filters/global-exception.filter.ts:85-91` |
| **Why it's a problem** | The `CorrelationIdMiddleware` attaches `x-correlation-id` to incoming requests and makes it available on `request.headers`, but the `GlobalExceptionFilter` does not include it in error responses. This makes it harder to correlate error responses with server-side logs during debugging. |
| **Recommended fix** | Add `correlationId` to the error response body, read from `request.headers["x-correlation-id"]`. |

## Architecture Findings

### Finding A1 — AuthGuard Catches and Re-throws with Generic Message (Low)

| Field | Value |
|-------|-------|
| **Severity** | Low |
| **Affected files** | `auth/authorization/guards/auth.guard.ts:48-49` |
| **Why it's a problem** | The guard's catch block catches ALL errors and throws a new `UnauthorizedError("Invalid or expired access token")`. This means if `jwtService.verifyAccessToken()` throws an error for an unexpected reason (e.g., malformed token, crypto failure), the original error details are lost and replaced with a generic message. While this prevents information leakage, it makes debugging authentication failures harder. |
| **Recommended fix** | Log the original error before re-throwing: `this.logger.warn(...)` or pass the original error as cause: `new UnauthorizedError("Invalid or expired access token", { cause: error })`. |

### Finding A2 — Silent Initialization Failure in PrismaService (Informational)

| Field | Value |
|-------|-------|
| **Severity** | Informational |
| **Affected files** | `prisma/prisma.service.ts:22-23` |
| **Why it's a problem** | `PrismaService.onModuleInit` has `try { await this.$connect() } catch { rootLogger.warn("Could not connect to PostgreSQL") }`. If the database connection fails at startup, the application continues to start and accept HTTP requests. Any subsequent query will fail with a confusing error. This contradicts NestJS best practices of failing fast on critical dependency failures. |
| **Recommended fix** | Either throw on connection failure (fail-fast) or implement a health check that reports database unavailability. |

### Finding A3 — Inline Comment Artifact (Informational)

| Field | Value |
|-------|-------|
| **Severity** | Informational |
| **Affected files** | `knowledge/services/document.service.ts:145` — `throw new NotFoundError("Document" /* deleted */);` |
| **Why it's a problem** | A stale inline comment `/* deleted */` was left in the code from the standardization. This is a code quality issue — the comment was intended to explain why "Document" was passed without an ID but should be either removed or formatted properly. |
| **Recommended fix** | Remove the inline comment or change to proper JSDoc. |

## Items Explicitly Verified as Correct

The following areas were reviewed and found to have **no issues**:

1. **GlobalExceptionFilter design** — Correctly uses `@Catch()` for all exceptions; distinguishes `HttpException`, `AppError`, and plain `Error`; returns consistent `{ statusCode, code, message, timestamp, path, details? }` format.

2. **AppError hierarchy** — Clean abstract base class with 9 concrete subclasses, each with correct HTTP status codes, error codes, and retryable flags. Properly handles `cause` chaining.

3. **TASK-1119 throw replacement** — All 89 `throw new Error(...)` correctly replaced with appropriate `@atlas/errors` subclasses. No misplaced status codes detected.

4. **Auth controller simplification** — Replacing message-string matching with `instanceof AppError` checks is a correct improvement per NestJS best practices.

5. **AI provider error handling** — Outer catch block correctly converts `AiProviderError` to structured `{ success: false, error: {...} }` return. The `AiProviderError` never leaks to HTTP responses.

6. **Correlation ID middleware** — Correctly attaches `x-correlation-id` header; middleware order in `app.module.ts` is correct (security headers → correlation → logging).

7. **ValidationPipe configuration** — `whitelist: true`, `forbidNonWhitelisted: true`, `stopAtFirstError: true` follow NestJS best practices for API validation.

8. **AuthGuard flow** — Correctly extracts Bearer token, verifies JWT, attaches claims to request. Uses `@atlas/errors` `UnauthorizedError` for consistent handling.

9. **TASK-1118 API key move to constructor** — All 8 AI providers now read API keys in constructor via `this.configure()` instead of module-level `const apiKey = process.env[...]`. Correct per NestJS DI best practices.

10. **Provider error return pattern** — Discriminated union `{ success: true, data } | { success: false, error }` is a well-established pattern for external service integration.

11. **No 'any' type usage** — All replacements use strongly typed AppError subclasses. No `any` was introduced.

12. **No circular dependencies** — The existing `forwardRef()` in `AiGatewayModule ↔ AgentRuntimeModule` was audited in TASK-1118 and documented as deferred tech debt. No new circular deps introduced.
