# SECURITY_AUDIT.md

> Baseline audit перед Phase 3. Только анализ, код не изменялся.
> Дата: 2026-07-17. Источники: секрет-скан (grep), `.env.example`, `pnpm audit`, GitHub Actions, Docker, configs.

## 1. Результаты секрет-скана

Сканирование всего репозитория (исключая `node_modules/.next/.output/dist/.turbo/.wxt`):

- **Реальных секретов не найдено.** Ни одного DSN, API-key, JWT, private-key или cloud-token в исходном коде.
- Единственные совпадения grep — **false positives**: имена файлов отчётов (`TASK_1126.md` и т.п.), имя пакета `check-disk-space` в lockfile.
- `.env.example` содержит **только пустые плейсхолдеры** (`OPENAI_API_KEY=`, `JWT_SECRET=`, `SENTRY_DSN=`, …). Эти значения не являются реальными секретами.

### Замечание (низкий риск)
`.env.example` содержит дефолтные креды локального MinIO:
```
STORAGE_ACCESS_KEY=minioadmin
STORAGE_SECRET_KEY=minioadmin
```
Это документированные дефолты для локальной разработки, НЕ прод-секреты. **Рекомендация:** оставить как есть для dev, но убедиться, что прод использует реальные значения через CI secrets (не через `.env.example`).

## 3. Рекомендации по безопасности (минимальные)

1. **Не блокирует Phase 3.**
2. Убедиться, что `.env.example` никогда не коммитится с реальными значениями (проверить `.gitignore` покрывает `.env`, `.env.local`).
3. При добавлении реальной телеметрии (Phase 3, P3-5) использовать **только** `process.env.NEXT_PUBLIC_POSTHOG_KEY` / `process.env.SENTRY_DSN` из CI secrets — не хардкодить.
4. Прод-секреты (DB, Redis, MinIO, JWT_SECRET) должны поступать через оркестратор секретов, а не через `.env.example`.

## 4. Инструменты
