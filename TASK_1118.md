## 3. Найденные проблемы

### Проблема 1: Module-level API key reads (8 AI providers) — Critical

**Где:** `providers/openai/openai.provider.ts:31-32`, `providers/anthropic/anthropic.provider.ts:33-34`, `providers/gemini/gemini.provider.ts:34-35`, `providers/deepseek/deepseek.provider.ts:31-32`, `providers/mistral/mistral.provider.ts:31-32`, `providers/groq/groq.provider.ts:31-32`, `providers/xai/xai.provider.ts:31-32`, `providers/openrouter/openrouter.provider.ts:31-32`

**Почему проблема:**
- API keys читаются из `process.env` на уровне модуля (при импорте файла), а не при инстанцировании класса
- Значения захватываются ДО того, как DI контейнер готов, и не могут быть сконфигурированы через DI
- Невозможно замокать ключи в тестах (они уже захвачены при импорте)
- Runtime-ротация ключей невозможна
- При отсутствии env-переменной провайдер создается с `apiKey: undefined` без валидации на старте

**Как исправлено:**
- Удалены module-level `const apiKey = process.env[...]` декларации
- Удалены spread-операторы `...(apiKey !== undefined ? { apiKey } : {})` из field initializer
- В конструктор добавлено чтение из `process.env` с вызовом `this.configure({ apiKey })`
- 8 файлов изменено

**Risk Assessment:**

| Change | Compatibility | Runtime Risk | Breaking Change |
|--------|---------------|-------------|-----------------|
| Move API key read to constructor | Fully compatible — same env var, same value, same configuration object | Zero — constructor runs before any method call; results in identical runtime state | No — public API unchanged, configuration contract unchanged |

### Проблема 2: Module-level config initialization в RedisService — High

**Где:** `redis/redis.service.ts:23` — `const DEFAULT_CONFIG = loadRedisConfig()`

**Почему проблема:**
- Redis config читается на уровне модуля, а не в конструкторе
- Нельзя переконфигурировать Redis через DI или env vars без перезапуска модуля
- Нарушает принцип DI — конфигурация должна быть инъекцией, не импортом

**Как исправлено:**
- Удалена module-level функция `loadRedisConfig()` и константа `DEFAULT_CONFIG`
- Конфигурация читается в конструкторе `super()` через inline-блок
- Упрощен вывод логов (убрано дублирование host/port в onModuleInit, т.к. это есть в классе)

**Risk Assessment:**

| Change | Compatibility | Runtime Risk | Breaking Change |
|--------|---------------|-------------|-----------------|
| Move Redis config to constructor | Fully compatible — same env vars, same defaults | Zero — constructor runs before `onModuleInit`; identical runtime state | No — public API unchanged, Redis interface unchanged |

### Проблема 3: Module-level version constant в HealthService — Low

**Где:** `health/health.service.ts:38` — `const APP_VERSION = process.env["npm_package_version"]`

**Почему проблема:**
- Версия захватывается при импорте модуля
- В тестах и при разных окружениях версия может быть актуальной на момент импорта, а не на момент запроса

**Как исправлено:**
- Удалена module-level `const APP_VERSION`
- `npm_package_version` читается внутри `createBuildInfo()` и `createBaseStatus()` через `process.env` при каждом вызове
- `const START_TIME = Date.now()` заменена на `private readonly startTime = Date.now()` в классе
- `createBaseStatus` принимает `uptime` параметр от класса вместо использования глобального `START_TIME`

**Risk Assessment:**

| Change | Compatibility | Runtime Risk | Breaking Change |
|--------|---------------|-------------|-----------------|
| Move version read to call-site | Fully compatible — same env var, same value path | Zero — `process.env` is accessible at any time; results identical | No — response schema unchanged |
| Move START_TIME to instance property | Fully compatible — same `Date.now()` call | Zero — `this.startTime` initialized in constructor, same value | No — public API unchanged |

### Проблема 4: S3 credentials default to empty string — Medium

**Где:** `knowledge.module.ts:36-37`

**Почему проблема:**
- `accessKeyId` и `secretAccessKey` при отсутствии env-переменных задаются как `""` (пустая строка)
- При попытке подключения к S3/MinIO с пустыми кредами возникнет запутанная ошибка авторизации, а не понятное сообщение "access key not configured"

**Как исправлено:**
- Заменено `?? ""` на conditional spread:
  ```typescript
  ...(process.env["..."] !== undefined ? { key: process.env["..."] } : {})
  ```
- При отсутствии env-переменных ключи не передаются в S3StorageConfig, что позволит сервису корректно обработать отсутствие конфигурации

**Risk Assessment:**

| Change | Compatibility | Runtime Risk | Breaking Change |
|--------|---------------|-------------|-----------------|
| Remove empty string defaults | Fully compatible — both `""` and `undefined` are falsy; code handles both | Zero — `S3FileStorageService` treats missing credentials the same as empty credentials (both result in auth error from AWS SDK) | No — creds are optional at transport level; only auth behavior changes from confusing error to SDK-native error |

| Alternative | Reason Rejected | Why Selected Solution is Preferred |

|-------------|-----------------|------------------------------------|

## 6. Architectural Decision Records

### ADR-001: Move AI Provider API Key Initialization to Constructor

- **Decision:** AI provider API keys will be read from `process.env` in the class constructor instead of at module evaluation time.
- **Status:** Accepted
- **Context:** 8 AI provider classes read their API key at the module level (`const apiKey = process.env[...]`). This prevents DI-based configuration, makes mocking impossible in tests, and bakes config at import time.
- **Alternatives:**
  - Factory provider with `useFactory` — rejected as too invasive
  - Inject `CONFIG_LOADER` — rejected because `load()` is single-call
  - Keep module-level — rejected because it prevents testability
- **Consequences:** Positive — providers become testable, config is read at DI time. Neutral — same env var contract. No negative consequences identified.

### ADR-002: Move Redis Config Initialization to Constructor

- **Decision:** Redis configuration will be read from `process.env` inline in the constructor instead of via a module-level function call.
- **Status:** Accepted
- **Context:** `const DEFAULT_CONFIG = loadRedisConfig()` reads env vars at module level, preventing DI-based configuration and making per-instance config impossible.
- **Alternatives:**
  - Inject config via `useFactory` — rejected as overengineered for a single service
  - Keep module-level — rejected because it violates DI patterns
- **Consequences:** Positive — config tied to constructor lifecycle. Neutral — same env vars, same defaults. No negative consequences.

### ADR-003: Move Version Reading from Module-Level to Call-Site

- **Decision:** `npm_package_version` will be read at call time inside helper functions, not captured at module level.
- **Status:** Accepted
- **Context:** `const APP_VERSION = process.env["npm_package_version"]` at module level captures version at import time. While acceptable for most production scenarios, it creates a stale reference in long-running test suites and prevents per-request version control.
- **Alternatives:**
  - Keep module-level — rejected because it creates untestable global state
  - Inject via DI — rejected as overengineered for a single env var
- **Consequences:** Positive — version is always fresh. Negative — negligible overhead of reading process.env on each health check. Acceptable trade-off.

### ADR-004: Remove Empty String Defaults for S3 Credentials

- **Decision:** S3 credentials will use conditional spread instead of `?? ""` defaults.
- **Status:** Accepted
- **Context:** `accessKeyId` and `secretAccessKey` default to empty string when env vars are not set, causing confusing AWS SDK auth errors instead of clear missing-configuration errors.
- **Alternatives:**
  - Keep `""` defaults — rejected because empty string behaves differently from undefined in AWS SDK
  - Add comprehensive validation — rejected because S3 config is optional (local storage doesn't need it)
- **Consequences:** Positive — missing credentials are cleanly absent, SDK provides native error. Negative — none.

## 12. Lessons Learned

### Module Initialization
Module-level `const` initialization from `process.env` is a common anti-pattern in NestJS codebases. It works by coincidence (modules are loaded synchronously before DI starts), but breaks testability and prevents DI-based configuration. Constructor-level initialization is always preferred for injectable services.

### Configuration Management
The `ConfigLoader` from `@atlas/config` provides validation (type checking, required fields, defaults) but is only used for `PORT` and `HOST` in `main.ts`. A future task should extend it to cover all env vars, enabling fail-fast validation at startup instead of runtime errors from missing configuration.

### Dependency Injection
Classes that read config at module level cannot be tested in isolation — the env var must be set globally before the module is loaded, affecting all tests in the suite. Constructor-level reads with `configure()` delegation allow per-instance mocking without global side effects.

### Testability
The `configure()` method pattern (present on all AI providers) enables DI-based configuration and testing. It was underutilized — providers created their config in field initializers instead of calling `configure()`. The fix aligns the implementation with the existing API contract.
