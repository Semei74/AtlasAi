## 1. Existing Architecture

### Health Subsystem (pre-TASK-1116)
- `HealthService` was a monolithic class with hardcoded checks for each dependency
- Constructor injected `PrismaService`, `RedisService`, `MetricsService` directly
- Private methods `checkStorage()` and `checkSearch()` contained inline HTTP fetch logic
- Adding a new health check required modifying `HealthService` — violated Open/Closed principle
- All business logic (metrics recording, error handling, status computation) was tightly coupled

### Prisma Seed
- Single `prisma/seed.ts` file contained all seed logic (user, org, workspace, membership, category)
- No modularity — adding new seed data meant growing the single file

### Documentation
- README was 936 lines — contained overlapping concerns (spec, setup, deployment, troubleshooting)
- No dedicated operational docs for deployment, development, or troubleshooting

## 2. Architectural Problems

| Problem | Impact |
|---------|--------|
| HealthService violates SRP | Knows about Prisma, Redis, HTTP, env vars, metrics |
| Adding new health check requires modifying HealthService | Scalability issue — every new subsystem (AI Gateway, Agents, MCP, Vector DB) needs a health check |
| No `HealthContributor` interface | No contract for contributors, no polymorphism |
| Metrics recording mixed with health check logic | Violates single responsibility — contributor should own its metrics |
| Seed logic in single file | Poor maintainability for growing seed data |
| README is bloated | Hard to find information, not a good entry point |
| No `make doctor` | Developers must manually check environment |

## 3. Implemented Solution

### 3.1 Health Architecture

**New interface:**
```typescript
// health/health-contributor.interface.ts
export type HealthStatusValue = "connected" | "disconnected" | "not_checked";

export interface HealthContributor {
  readonly name: string;
  check(): Promise<HealthStatusValue>;
}

export const HEALTH_CONTRIBUTORS = Symbol("HEALTH_CONTRIBUTORS");
```

**Four contributors created:**
- `DatabaseHealthContributor` — encapsulates Prisma `SELECT 1`, metrics timer, error handling
- `RedisHealthContributor` — encapsulates Redis `PING`, metrics timer, error handling
- `StorageHealthContributor` — encapsulates MinIO health endpoint fetch, env var check
- `SearchHealthContributor` — encapsulates OpenSearch health endpoint fetch, env var check

**Refactored HealthService:**
- Constructor: `@Inject(HEALTH_CONTRIBUTORS) contributors: HealthContributor[]`
- `readiness()` runs all contributors in parallel via `Promise.all`, aggregates results by name
- Builds dependency map from contributor results — no knowledge of individual checks
- Same `ReadinessStatus` interface (backward compatible)

**HealthModule:**
- Registers each contributor as a provider
- Uses `useFactory` to collect them into a single `HEALTH_CONTRIBUTORS` array
- Adding new contributor: create class, add to providers + inject array

### 3.2 Seed Refactoring

```
prisma/
├── seed.ts                          # Root orchestrator
└── seed/
    ├── users.seed.ts                # DEFAULT_ADMIN_ID exported
    ├── organizations.seed.ts        # DEFAULT_ORG_ID exported
    ├── workspaces.seed.ts
    ├── memberships.seed.ts
    └── prompt-categories.seed.ts    # DEFAULT_CATEGORY_ID exported
```

Each seed file:
- Takes `PrismaClient` as parameter (no global state)
- Exports its constants (UUIDs) for cross-referencing
- Uses `upsert` for idempotency
- Returns typed results for dependency chaining

Root orchestrator calls seeds in dependency order (users → orgs → workspaces → memberships → categories).

## 6. Architecture Decisions

| Decision | Rationale |
|----------|-----------|
| Single `HEALTH_CONTRIBUTORS` token with `useFactory` | Avoids NestJS multi-provider complexity; clear DI registration in one place |
| `Promise.all` over sequential execution | Health checks are independent — parallel is faster |
| Name-based result aggregation | Contributors self-identify by name; no positional coupling |
| Contributors own their metrics | Each contributor knows what metrics to record; no central metrics logic |
| `Process.env` in Storage/Search contributors | These checks don't need DI — env vars are the cleanest dependency |
| Seed files accept `PrismaClient` parameter | No global/singleton PrismaClient; testable and explicit |
| Seed orchestrator controls order | Users → Orgs → Workspaces → Memberships → Categories |
| README rewritten to 90 lines | Entry point should be concise; operational detail belongs in docs/ |
| `make doctor` as shell script | Zero dependencies; works without Node.js/pnpm |

- Metrics recording moved into contributors — same instruments, same performance
- No new allocations in hot paths
- Seed files use `upsert` — minimal DB overhead on repeated runs

## 14. Remaining Limitations

1. **Docker unavailable** — production build and compose deploy cannot be verified
2. **TestSprite blocked** — server cannot start for API-level validation
3. **Health contributors tightly coupled to HealthModule** — adding a contributor requires modifying the module file. An `@HealthContributor()` decorator with auto-discovery would eliminate this, but adds complexity disproportionate to current needs.
4. **Storage and Search contributors read env vars directly** — no test coverage for the `connected`/`disconnected` paths (only `not_checked` is tested, since env vars aren't set in test environment)
5. **Seed files not tested** — no seed test suite. Manual verification required against a running database.
6. **OpenSearch health check assumes security disabled** — production OpenSearch clusters with `plugins.security.enabled: true` would need authentication headers.
