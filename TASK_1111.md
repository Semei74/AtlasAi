## Детали по исправленным пунктам

### C1 — Тесты на `DocumentController.create` ✅
Новый файл `src/ai-gateway/knowledge/controllers/document.controller.test.ts` (17 тестов),
покрывает критический путь загрузки:
- успешная загрузка + проброс `identity`/`metadata` из токена;
- **`organizationId` извлекается из токена, значение из тела игнорируется** (защита от cross-tenant);
- пропуск необязательных полей;
- отказ 400 по недопустимому MIME;
- **отказ 413 по превышению размера** (`PayloadTooLargeException`);
- отказ 400 при отсутствии файла;
- проброс неожиданных ошибок multipart / сервиса;
- отказ при отсутствии пользователя / организации.

### C2 — Тесты на `assertArchiveEntriesSafe`, без мока `parser-limits` ✅
Новый `src/ai-gateway/knowledge/services/parsers/parser-limits.security.test.ts`
использует **реальные zip-архивы** (сгенерированы через `jszip`, без `vi.mock`):
- валидный/пустой архив принимается;
- архив с 10 001 записью → отказ `/too many entries/`;
- искусственно завышенный `uncompressedSize` (201 MB) → отказ `/decompressed size exceeds/`;
- в пределах лимита → принимается;
- `assertArchiveWithinSize` — буфер > 50 MB отклоняется, ≤ — принимается.

Дополнительно интеграционные тесты без мока:
- `docx.parser.security.test.ts` — минимальный docx парсится; docx-бомба (10 001 запись) отклоняется;
- `format-parsers.security.test.ts` — epub/pptx: относительные/абсолютные `href` резолвятся
  только внутри архива (нет обращения к ФС), вложенные каталоги, дубликаты spine, пустой архив.

> Примечание: `format-parsers.test.ts` по-прежнему мокает `parser-limits.js` для юнит-путей
> парсеров, но защита покрыта отдельными security-тестами без мока (C2 удовлетворён).

### D — docx zip-bomb защита ✅
`src/ai-gateway/knowledge/services/parsers/docx.parser.ts:16-22`:
```ts
assertArchiveWithinSize(buffer);            // сжатый лимит 50 MB
const zip = await JSZip.loadAsync(buffer);
assertArchiveEntriesSafe(zip);              // ≤10 000 записей, ≤200 MB распакованного
const result = await mammoth.convertToHtml({ buffer });
```
Используется существующий `parser-limits` (DRY, без новой архитектуры). Поведение
`assertArchiveEntriesSafe` подтверждено через Context7 (`jszip` `_data.uncompressedSize`).

### A — 413 вместо 500, удалён мёртвый `MAX_FILE_SIZE` ✅
`src/ai-gateway/knowledge/controllers/document.controller.ts`:
- `isMultipartFileTooLarge(error)` (строки 43-49) распознаёт `FST_REQ_FILE_TOO_LARGE`;
- `create()` (строки 79-94) оборачивает `multipart.toBuffer()` в try/catch и бросает
  `PayloadTooLargeException("File exceeds the maximum allowed size of 50 MB")`;
- удалён `const MAX_FILE_SIZE` и мёртвый чек `buffer.byteLength > MAX_FILE_SIZE`
  (реальное ограничение — `fileSize` в плагине multipart в `main.ts`).

### H — Дублирующаяся логика `mkdir` ✅
`src/ai-gateway/knowledge/services/local-file-storage.service.ts:12-18`: вместо двух
избыточных вызовов `mkdir` (включая запутанный `new URL(...).pathname.replace(...)`)
— единый `await mkdir(dirname(fullPath), { recursive: true })`.

## Закрытые с обоснованием (не требуют кода)

### E — `@Global()` на `AuthModule` ⚪
`src/auth/auth.module.ts:46` сохранён как `@Global()`. Анализ:
- `AuthModule` явно импортирован только в `app.module.ts:23` и `tenant.module.ts:8`;
- остальные модули (knowledge, ai-gateway, membership, workspace, organization, metrics,
  prompt-library) полагаются на глобальную видимость;
- **важно:** `AuthGuard` импортируется в контроллерах напрямую из файла гварда
  (`authorization/guards/auth.guard.js`), а не через экспорт модуля; межмодульных
  инъекций `AuthService` нет (проверено `grep`-ом).
- Удаление `@Global()` — скоординированный рефакторинг ~5 модулей с риском регрессии,
  вне scope hardening-задачи и не влияет на границу безопасности (гвард импортируется явно).
  **Рекомендация:** вынести в отдельную задачу по архитектурному долгу.

### I — `CreateDocumentDto.organizationId` ⚪
Поле оставлено в DTO (часть публичного контракта API). Контроллер созадательно игнорирует
значение тела и берёт `organizationId` из токена — это корректная защита. Удаление поля из DTO
является breaking change для клиентов; не требуется для безопасности.

### L — Мёртвая инфраструктура OpenSearch ⚪
`docker/docker-compose.yml:101` и `.env.example:41` провизионируют OpenSearch, но
`grep -rin "opensearch|SEARCH_HOST" src/` → **0 совпадений**. Бэкенд никогда не обращается
к поиску. **Рекомендация:** удалить сервис из compose и переменные окружения, либо
реализовать интеграцию, чтобы инфраструктура не простаивала.

### J / K — Принятые (low risk) 🟡
- `xml.parser.ts`: regex-парсер неточен для сложного XML, но **безопасен от XXE**
  (не использует DOM-парсер). Вне scope hardening.
- MIME: валидируется по клиентскому `mimetype`. Прямой уязвимости нет — реальная защита
  от вредоносного содержимого обеспечивается лимитами размера (50 MB сжатый,
  200 MB распакованный, ≤10 000 записей). Content-sniffing — улучшение defense-in-depth,
  вынесено за рамки.
