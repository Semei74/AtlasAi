## Existing Architecture

### Exception Flow

```
Service (throw AppError/HttpException/Error)
  → Controller (optional catch: metrics + re-throw)
    → GlobalExceptionFilter (@Catch())
      → Structured JSON response: { statusCode, code, message, timestamp, path, details? }
```

### GlobalExceptionFilter Behavior

- Registered via `APP_FILTER` in `app.module.ts`
- Handles three exception types:
  - `HttpException` → status from `getStatus()`, code mapped from status map
  - `AppError` (from `@atlas/errors`) → status from `.httpStatus`, code from `.code`, optional `.details`
  - Plain `Error` → `500 Internal Server Error`
- Always returns `{ statusCode, code, message, timestamp, path, details? }`
- Logs `Unhandled exception: {message}` with stack trace for every Error

### Existing Custom Exceptions (`@atlas/errors`)

All available from `packages/errors/src/index.ts`:

| Class | HTTP Status | Code | Retryable |
|-------|-------------|------|-----------|
| `ValidationError` | 422 | VALIDATION_ERROR | false |
| `NotFoundError` | 404 | NOT_FOUND | false |
| `UnauthorizedError` | 401 | UNAUTHORIZED | false |
| `ForbiddenError` | 403 | FORBIDDEN | false |
| `ConflictError` | 409 | CONFLICT | false |
| `InternalError` | 500 | INTERNAL_ERROR | true |
| `RateLimitError` | 429 | RATE_LIMITED | true |
| `AiProviderError` | 503 | AI_PROVIDER_ERROR | true |
| `ConfigurationError` | 500 | CONFIGURATION_ERROR | false |

These classes were already used by `AuthGuard` (throws `UnauthorizedError`) and handled by `GlobalExceptionFilter`. The task reused this existing infrastructure — no new exception classes were introduced.

### Validation

`ValidationPipeProvider` (`common/pipes/validation-pipe.provider.ts`) is registered via `APP_PIPE` and returns UNPROCESSABLE_ENTITY (422) for class-validator errors.

### Catch-and-Convert Pattern (Auth Controllers)

`AuthController` previously caught `Error` from services and used message-string matching to re-throw as NestJS HTTP exceptions:

```typescript
catch (error) {
  if (error instanceof Error && error.message === "Email already registered") {
    throw new ConflictException(error.message);
  }
  throw error;
}
```

This was replaced with `instanceof AppError` checks after standardizing service throws.

## Problems Found

### Problem 1: `throw new Error(...)` in Services (89 occurrences)

All 89 `throw new Error(...)` calls in production service code propagated to the `GlobalExceptionFilter` as plain `Error` objects, resulting in `500 Internal Server Error` regardless of the actual failure type. Common patterns:

| Pattern | Count | Impact |
|---------|-------|--------|
| Auth failures (invalid creds, expired tokens) | 22 | Returned 500 instead of 401 |
| Not found errors (document, session, version) | 18 | Returned 500 instead of 404 |
| Validation errors (metadata, limits, MIME) | 23 | Returned 500 instead of 422 |
| Provider API errors | 10 | Returned 500 instead of 503 |
| Config errors (boot-time) | 5 | Returned 500 (crashed process — acceptable) |
| Other (conflict, forbidden, streaming) | 11 | Various incorrect status codes |

### Problem 2: Message-String Matching in Controllers

`AuthController` used brittle message-string matching (`error.message === "Email already registered"`) to determine HTTP status codes. This couples controller logic to service implementation details.

### Problem 3: Stack Trace Leakage for Unknown Errors

The `GlobalExceptionFilter` already sanitizes responses (returns generic "Internal Server Error" for plain `Error`). No change needed.

## Root Cause Analysis

The root cause was a missing architectural convention: services should throw typed exceptions (`AppError` subclasses or `HttpException`) rather than generic `Error`. The `@atlas/errors` package already provided the exception hierarchy, but services were not using it.

## Architectural Decisions

### ADR-001: Reuse `@atlas/errors` AppError Hierarchy

- **Decision**: All service-layer `throw new Error(...)` calls are replaced with existing `@atlas/errors` AppError subclasses.
- **Rationale**: These classes were already defined, tested, and handled by `GlobalExceptionFilter`. Introducing new exception classes would duplicate existing infrastructure.
- **Consequences**: Zero new classes needed. All 89 replacements use 7 existing AppError subclasses.

### ADR-002: Replace Message-String Matching with instanceof

- **Decision**: Auth controller catch blocks now use `instanceof UnauthorizedError` / `instanceof ConflictError` instead of `error.message === "...".
- **Rationale**: Message-string matching is brittle — renaming a message string in the service silently breaks the controller. Type-based matching is refactor-safe.
- **Consequences**: Controllers are decoupled from service message text.

### ADR-003: Preserve 401 Behavior for Refresh Endpoint

- **Decision**: The `/auth/refresh` endpoint continues to return 401 for all refresh token errors, even though services now throw typed exceptions that would map to different status codes (e.g., `ConflictError` → 409, `NotFoundError` → 404).
- **Rationale**: Changing the HTTP status code for refresh token errors would be a breaking change for API clients that expect 401 for all token-related failures.
- **Documented in**: `auth.controller.ts`, `refresh` method catch block.

### ADR-004: Leave AI Provider Throws Unchanged

- **Decision**: AI provider `throw new AiProviderError(...)` calls are caught internally by the provider's outer catch block and returned as structured `{ success: false, error: {...} }` responses. The `AiProviderError` is never seen by the `GlobalExceptionFilter`.
- **Rationale**: The `AiProviderError` is used for type consistency and future-proofing, even though it's caught internally today.

## Alternatives Considered

| Alternative | Rejected Because |
|-------------|-----------------|
| Create new custom exception classes | Would duplicate `@atlas/errors` which already has 9 subclasses |
| Use NestJS HTTP exceptions in all services | NestJS HTTP exceptions are HTTP-layer concerns; `@atlas/errors` are domain exceptions preserved across layers |
| Keep `throw new Error()` in boot-time config | `ConfigurationError` is more descriptive and consistent with the overall pattern |
| Return error objects instead of throwing | Would require refactoring all service methods to return `Result<T, E>` — a breaking architectural change outside this task scope |

### Behavior Change Detail

Some client code that catches errors by message text may break. For example:
- Previously: `"Document not found"` → Now: `"Document with id 'doc-1' not found"`
- Previously: `"Provider 'openai' is not registered"` → Now: `"Provider with id 'openai' not found"`

Clients should use HTTP status codes or `error.code` fields for error handling, not message text.

## Lessons Learned

1. **Always use typed exceptions**: String-based error handling is brittle. `instanceof` checks are refactor-safe.

2. **Existing infrastructure is often sufficient**: The `@atlas/errors` package had all the exception classes needed. No new classes were required.

3. **Boot vs runtime error handling**: Config errors at boot time should crash the process with a clear message. Runtime errors should flow through the GlobalExceptionFilter for consistent HTTP responses.

4. **Provider error patterns**: AI providers use a catch-and-return pattern (never throw to the caller). This is intentional — it allows granular error reporting with latency metrics. The `AiProviderError` class is used internally for consistency.

5. **Test fragility with string matching**: Several tests used `.toThrow("exact message string")` which broke when messages changed to include more context (e.g., resource IDs). Use `.toThrow(/partial pattern/)` or check error type instead.
