## 1. Architecture Decisions

### AD-001: Design System as Documentation Only

**Decision:** The Enterprise Design System exists as Markdown documentation in `docs/design/`. No code generation, no Figma tokens, no Stitch prompts.

**Rationale:**
- Documentation is the source of truth; code is generated by Stitch based on these docs.
- Avoids duplication of design rules in multiple formats.
- Markdown is version-controllable, reviewable, and accessible to all team members.
- Future tooling (token export, Figma sync, code gen) will read from these docs.

**Consequence:** All implementation work references these documents as authority.

### AD-002: Single Source of Truth per Concept

**Decision:** Each design concept is defined in exactly one document. Cross-references use relative links.

**Rationale:**
- Avoids contradictory specifications.
- A designer or developer only needs to update one place.
- The `ENTERPRISE_DESIGN_SYSTEM.md` acts as the table of contents and overview.

**Example:** Color tokens are ONLY in `COLOR_SYSTEM.md`. The component library references color tokens by name. Typography is ONLY in `TYPOGRAPHY_SYSTEM.md`.

### AD-003: 8px Base Grid

**Decision:** All spacing uses an 8px base unit with 4px micro exceptions.

**Rationale:**
- 8px divides evenly into common screen widths (320, 375, 768, 1024, 1440).
- 8px provides sufficient granularity for UI spacing without overwhelming choices.
- 4px micro unit handles edge cases (icon gaps, dense data).
- Consistent with Material Design 3 and major enterprise design systems.

**Explicitly not chosen:** 5px grid (too granular), 10px grid (doesn't divide into 320/768/1024).

### AD-004: Inter as Single UI Font

**Decision:** Inter is the sole UI font family.

**Rationale:**
- Inter was purpose-built for UI screens (tall x-height, clear letterforms).
- Variable font support (single file for all weights).
- Excellent number legibility (tabular figures available).
- Open source license (SIL OFL), no commercial restrictions.
- Superior screen rendering at all sizes compared to system fonts.

**Alternatives considered and rejected:**
- **SF Pro:** Apple-only, requires licensing for web.
- **Roboto:** Generic, less distinctive, weaker tabular figures.
- **System UI stack:** Inconsistent across platforms, no unique brand identity.

### AD-005: Lucide as Icon Library

**Decision:** Lucide is the sole icon library.

**Rationale:**
- 1,450+ icons with consistent 1.5px stroke.
- Active community (weekly releases, fast issue resolution).
- Tree-shakeable — import only used icons, no bundle bloat.
- SVG-based (no font dependency, no layout shift).
- Clean geometric style matching Atlas AI aesthetic.
- ISC license (permissive, no attribution required).

**Alternatives considered and rejected:**
- **Material Symbols:** Google-centric aesthetic, variable fill/weight causes inconsistency.
- **FontAwesome:** Pro license required for latest icons, inconsistent stroke weights.
- **Heroicons:** Fewer icons (400 vs 1,450), slower release cycle.
- **Feather:** Deprecated (merged into Lucide).

### AD-006: Indigo Primary, Teal Secondary

**Decision:** Primary = Indigo (#4F46E5), Secondary = Teal (#0D9488), Accent = Amber (#F59E0B)

**Rationale:**
- **Indigo** conveys trust, intelligence, and enterprise stability (used by Stripe, Notion, Linear).
- **Teal** communicates growth, innovation, and technology (used by Slack, Twilio).
- **Amber** provides warm emphasis for highlights without competing with primary.
- High contrast against both light (#FFFFFF) and dark (#0F1117) backgrounds.
- Color-blind friendly (indigo/teal/amber are distinguishable by all common color blindness types).

### AD-007: Light and Dark Theme Parity

**Decision:** Dark theme is not an afterthought — every color token has a defined dark theme equivalent.

**Rationale:**
- Enterprise users often work late or in low-light environments.
- Dark mode reduces eye strain for data-heavy screens.
- Accessibility: dark mode must meet same WCAG ratios as light mode.
- User preference is respected via `prefers-color-scheme` and manual toggle.

**Key decisions:**
- Dark surfaces use cool charcoal (not pure black) — reduces eye strain.
- Shadows in dark mode are replaced with luminance (subtle light edge).
- Semantic colors are brightened (not darkened) for contrast against dark backgrounds.

### AD-008: WCAG 2.2 AA as Minimum Bar

**Decision:** Every color combination must meet WCAG 2.2 AA contrast ratios.

**Rationale:**
- Legal requirement for enterprise software in many jurisdictions.
- ~15% of population has some form of visual impairment.
- AA is achievable without sacrificing design quality.
- AAA pursued where possible but not mandated (except for critical text).

**Consequences:**
- Some decorative colors are intentionally low contrast (disabled states, default borders) and are noted in accessibility documentation.
- Focus rings always meet 3:1 minimum against surrounding background.
- All semantic text pairs meet AA ratios.

### AD-009: Components Documented by Spec, Not Code

**Decision:** Components are specified by purpose, variants, states, behavior, and specs — not by React code.

**Rationale:**
- The design system is framework-agnostic (React Native, Web, Future frameworks).
- Stitch generates code from specifications, not from existing code.
- Documentation focuses on behavior and appearance, not implementation.
- Specs can be translated to any framework without bias.

**Format:**
- Purpose: What the component does
- Variants: Visual/style variations
- States: Default, Hover, Active, Focus, Disabled, Loading, Error
- Spacing: Padding, margin, gap references to spacing tokens
- Behavior: Interaction patterns, keyboard navigation, accessibility
- Specs: Width, height, font, color, radius values

### AD-010: Enterprise Features Are First-Class

**Decision:** AI-specific components, permission gates, audit logs, and enterprise patterns are first-class citizens alongside primitives.

**Rationale:**
- Atlas AI is an enterprise AI platform — AI features are core, not add-ons.
- Enterprise requirements (audit, permission, security) are as important as visual design.
- Component library includes 12 AI-specific components and 14 enterprise composites.

## 2. Design Token Philosophy

### 2.1 Token Organization

Tokens are organized in three tiers:

```
Tier 1 — Global tokens:    Raw values (colors, sizes, fonts)
Tier 2 — Alias tokens:     Semantic mapping (primary-500 → --color-primary)
Tier 3 — Component tokens: Component-specific (--button-primary-bg)
```

### 2.2 Naming Convention

```
--{category}-{property}-{variant}

Examples:
--color-primary-500          (global color)
--color-bg-primary           (alias — background surface)
--button-primary-bg          (component token)
--space-inset-md             (semantic spacing)
```

### 2.3 Token Inheritance

```
Global → Alias → Component

Example:
#4F46E5 → --color-primary-500 → --color-primary → --button-primary-bg
#FFFFFF → --color-neutral-50 → --color-bg-primary → --page-background
```

## 4. Forbidden Patterns

These patterns are explicitly forbidden in Atlas AI UI. See [ENTERPRISE_DESIGN_SYSTEM.md §14.1](./ENTERPRISE_DESIGN_SYSTEM.md) for the complete list with rationale.

1. **Carousels** — Content discovery killers
2. **Hamburger menus as primary nav** — Hides navigation, increases cognitive load
3. **Infinite scroll without search** — User position loss
4. **Auto-play media** — Distracting, data-heavy
5. **Right-click only actions** — Accessibility failure
6. **Drag-and-drop only** — Not keyboard operable
7. **Toast for critical errors** — Easy to miss auto-dismissal
8. **Unsolicited modals** — Workflow interruption
9. **Color-only indicators** — Color blindness exclusion
10. **Disabling without explanation** — User frustration

## 5. Preferred Patterns

These patterns are the idiomatic Atlas AI approach to common UI challenges.

### 5.1 State Management

```
Data → Loading → Success / Empty / Error
```

Every data-driven component implements all four terminal states (success, empty, error) plus the transitional loading state.

### 5.2 Confirmation Pattern

```
Destructive action:
1. User clicks Delete
2. Dialog appears: "Delete X?" with description
3. User confirms by typing the item name (high value) or clicking button (low value)
4. Toast appears: "X deleted" with "Undo" action (soft delete)
```

### 5.3 Form Pattern

```
1. Display form with current values
2. Auto-save every 30 seconds
3. Show "Saved" indicator
4. On error: inline field errors + form-level error banner
5. On success: toast confirmation
6. On navigation away with unsaved changes: discard confirmation
```

### 5.4 Search Pattern

```
1. Global search in top bar (Cmd+K)
2. Results grouped by category
3. Keyboard navigation (arrow keys, Enter)
4. Recent searches shown when query is empty
5. "No results" state with suggestions
```

### 5.5 Notification Pattern

```
1. Real-time notifications arrive via toast (transient)
2. Notification center stores history (persistent)
3. Bell icon shows unread count badge
4. Notifications grouped: Today, Yesterday, Older
5. User can mark read/dismiss individual or all
```

## 6. Trade-off Matrix

| Decision | Pro | Con | Mitigation |
|----------|-----|-----|------------|
| 8px grid | Consistent, divisible by common widths | Occasional 4px needed | 4px micro token as exception |
| Inter single font | Brand consistency, one file | Less platform-specific optimization | System fallback stack handles missing fonts |
| Lucide only | Consistency, tree-shaking | Missing very niche icons | Custom SVG matching Lucide style |
| Indigo primary | Professional, trusted | Common (similar to Linear) | Distinguish through secondary teal |
| 14px base body | More content visible | Might be small for some users | 16px as default, 14px as compact option |
| Bottom tab nav (mobile) | Always visible, thumb reach | Limits to 5 tabs | +N overflow menu for more items |
| 4 KPI cards per row | Good density on desktop | Too tight on tablet | Responsive: 4→2→1 columns below 1024px |

### 7.2 Backward Compatibility

- Phase 1 documents are preserved (not deleted) for reference.
- New components reference Phase 2 tokens only.
- Stitch prompts should reference Phase 2 documents as authoritative.
- Migration period: Phase 1 docs deprecated but not removed for 1 release cycle.

### 7.3 When to Update

- **New component added:** Add to COMPONENT_LIBRARY.md
- **New color needed:** Add to COLOR_SYSTEM.md with WCAG verification
- **Token change:** Update the specific document, flag as breaking change
- **Pattern change:** Update ENTERPRISE_DESIGN_SYSTEM.md + impacted component specs
- **New screen type:** Add to SCREEN_LAYOUTS.md
