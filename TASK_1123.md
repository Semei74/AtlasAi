## Phase 1 — Critical Production Bugs

### P1.1 WorkflowRuntime Memory Leak (HIGH)

**File**: `src/ai-gateway/agents/workflow/services/workflow-runtime.service.ts`

**Before**: The `executions` Map (line 18) grew monotonically — entries were added in 8 code paths but never deleted. The companion `abortControllers` Map was properly cleaned up in 4 places.

**After**: Added `this.executions.delete(executionId)` alongside every existing `this.abortControllers.delete(executionId)`:

| Terminal Path | Status | Line |
|---|---|---|
| Successful completion | `abortControllers.delete` + **`executions.delete`** | 88-89 |
| Catch-block failure | `abortControllers.delete` + **`executions.delete`** | 113-114 |
| Cancel | `abortControllers.delete` + **`executions.delete`** | 138-139 |
| Resume completion | `abortControllers.delete` + **`executions.delete`** | 204-205 |

**Impact**: Eliminates unbounded memory growth under sustained workflow load.

### P1.2 Missing Composite Prisma Index (HIGH)

**File**: `prisma/schema.prisma` (KnowledgeDocument model)

**Before**:
```prisma
@@index([organizationId])
@@index([workspaceId])
@@index([ownerId])
@@index([status])
@@index([createdAt])
@@index([tags], type: Gin)
```

Every query filtered by `(organizationId, deletedAt)` (used in `findDocument`, `searchByMetadata`, etc.) could only use the single-column `organizationId` index and performed a heap scan for `deletedAt`.

**After**:
```prisma
@@index([organizationId])
@@index([organizationId, deletedAt])     // NEW
@@index([workspaceId])
```

**Impact**: Composite index enables efficient index-only lookups for the most common query pattern. No schema behavior change — purely additive.

### P1.3 Document Controller RBAC (HIGH / Security)

**File**: `src/ai-gateway/knowledge/controllers/document.controller.ts`

**Before**: All endpoints used only `@UseGuards(AuthGuard)` — any authenticated user (including Viewers) could create, update, archive, restore, and delete documents.

**After**: Added `@UseGuards(AuthGuard, RolesGuard)` + `@Roles("Owner", "Admin", "Manager", "User")` on all write endpoints:

| Endpoint | Guard Before | Guard After | Role Requirement |
|----------|-------------|-------------|-----------------|
| `POST /` (create) | AuthGuard | AuthGuard + RolesGuard | Owner/Admin/Manager/User |
| `PATCH :id` (update) | AuthGuard | AuthGuard + RolesGuard | Owner/Admin/Manager/User |
| `DELETE :id` (soft-delete) | AuthGuard | AuthGuard + RolesGuard | Owner/Admin/Manager/User |
| `POST :id/archive` | AuthGuard | AuthGuard + RolesGuard | Owner/Admin/Manager/User |
| `POST :id/restore` | AuthGuard | AuthGuard + RolesGuard | Owner/Admin/Manager/User |
| `GET /` (list) | AuthGuard | AuthGuard (unchanged) | Any authenticated user |
| `GET :id` (detail) | AuthGuard | AuthGuard (unchanged) | Any authenticated user |
| `GET :id/download` | AuthGuard | AuthGuard (unchanged) | Any authenticated user |

**Per the existing permission matrix**: Viewers have `files:read` only. Users have `files:create`, `files:read`, `files:update`, `files:delete`. Managers/Owners/Admins have full access.

### P1.4 Gemini API Key Exposure (HIGH / Security)

**File**: `src/ai-gateway/providers/gemini/gemini.provider.ts`

**Before**: API key transmitted as URL query parameter:
```typescript
const url = `${baseUrl}/models/${model}:generateContent?key=${key}`;
// Health check:
const url = `${baseUrl}/models/${model}?key=${key}`;
```

**After**: API key transmitted as `x-goog-api-key` HTTP header:
```typescript
const response = await fetch(url, {
  method: "POST",
  headers: { "Content-Type": "application/json", "x-goog-api-key": key },
});
// Health check:
const response = await fetch(url, {
  headers: { "x-goog-api-key": key },
  signal: controller.signal,
});
```

**Impact**: API key no longer appears in server logs, proxy logs, or referrer headers. Consistent with all other providers (OpenAI, Anthropic, Mistral, etc.) which use `Authorization: Bearer`. Google Gemini API supports `x-goog-api-key` header natively.

## Phase 2 — Observability

### P2.1 MetricsInterceptor Status Code (MEDIUM)

**File**: `src/metrics/metrics.interceptor.ts`

**Before**: All exception paths recorded `status_code="500"` regardless of actual HTTP status.

**After**: Added `getExceptionStatus()` helper that extracts the real status:
```typescript
function getExceptionStatus(error: unknown): number {
  if (error instanceof HttpException) return error.getStatus();
  if (error instanceof AppError) return error.httpStatus;
  return 500;
}
```

Now records correct status codes: 400, 401, 403, 404, 409, 422, 429, 500, etc. Metrics format unchanged.

**Impact**: Accurate HTTP error status distribution in Prometheus metrics.

### P2.2 trustProxy Configuration (MEDIUM)

**File**: `src/main.ts`

**Before**:
```typescript
new FastifyAdapter({ logger: false }),
```

**After**:
```typescript
new FastifyAdapter({
  logger: false,
  trustProxy: true,
}),
```

**Rationale**: `trustProxy: true` causes Fastify to trust `X-Forwarded-For` and `X-Forwarded-Proto` headers set by reverse proxies (ALB, NGINX, Traefik). Without it, `request.ip` returns the proxy's IP instead of the client IP, making IP-based audit logging inaccurate. Safe for local development — without a proxy, headers are absent and behavior is identical.

**Impact**: Accurate `request.ip` values in auth audit logs behind reverse proxy.

## Phase 3 — Performance

### P3.1 Parallel Logout (MEDIUM)

**File**: `src/auth/services/auth-orchestrator.service.ts`

**Before**:
```typescript
await this.sessionService.revokeAllUserSessions(userId, currentSessionId);
await this.jwtService.revokeAllUserTokens(userId);
```

**After**:
```typescript
await Promise.all([
  this.sessionService.revokeAllUserSessions(userId, currentSessionId),
  this.jwtService.revokeAllUserTokens(userId),
]);
```

**Impact**: LogoutAll latency reduced from sequential to parallel execution. Operations are independent (session store ↔ token store, different Redis key prefixes).

### P3.2 Parallel Login Cleanup (MEDIUM)

**File**: `src/auth/services/auth-orchestrator.service.ts`

**Before**:
```typescript
await this.lockoutService.clearFailedAttempts(lockoutId);
const user = await this.userRepository.findById(authResult.userId);
```

**After**:
```typescript
const [user] = await Promise.all([
  this.userRepository.findById(authResult.userId),
  this.lockoutService.clearFailedAttempts(lockoutId),
]);
```

**Impact**: Login latency reduced by approximately one Redis round-trip. Operations are independent (Redis lockout ↔ PostgreSQL user query).

### P3.3 Metadata History Optimization (MEDIUM)

**File**: `src/ai-gateway/knowledge/services/metadata.service.ts`

**Before**: Two sequential queries — `count()` then `findFirst()`:
```typescript
const existingCount = await this.prisma.knowledgeDocumentMetadataHistory.count({ ... });
if (existingCount > 0) {
  const latest = await this.prisma.knowledgeDocumentMetadataHistory.findFirst({ ... });
  if (latest !== null && latest.version >= document.version) return;
}
```

**After**: Single `findFirst()`:
```typescript
const latest = await this.prisma.knowledgeDocumentMetadataHistory.findFirst({ ... });
if (latest !== null && latest.version >= document.version) return;
```

**Impact**: Eliminates one redundant database query per metadata save. If count is 0, `findFirst` returns null (same as count=0). If count > 0, count was wasted (only checked `>0`).
